# GitHub README 写作

把 README 写成仓库的项目首页。读者扫过首屏，就能明白这是做什么的、下一步点哪里。照 [首屏与正文模板](assets/readme-template.md) 组织，按仓库的内容调整篇幅。

## 先确认项目实际能交付什么

- 根据用户给的仓库、链接或当前工作区确认项目名、仓库所有者和默认分支。查 README、目录树和真正的入口，例如扩展清单、安装包、命令、在线示例或使用文档。
- 涉及版本、平台、许可证、发布状态或截图时，用仓库文件或真实可访问的发布页面核实。目标仓库尚不可访问时，可写草稿并说明缺少哪些事实。
- 用户提供另一个托管、交付或协作平台时，把已核实且允许分享的项目入口加到首屏。仅存在本地文件、私有空间或预览链接时，用准确的链接文字说明适用范围。

## 先把首屏排出来

1. 一个醒目的大标题。产品已有图标，就用真实图标。加一句话说明给谁用、能完成什么。
2. 一排可点击徽章。优先展示版本、平台和已经确认的许可证或其他对读者有用的信息。徽章链接到对应依据或章节。
3. 一排可执行的链接。把最常用的动作放最前面，例如下载、在线体验、安装或直接看示例，其余再放用法、原理和反馈。下载源码 ZIP、可安装的成品和商店入口分别用准确名称。

## 正文按读者的使用次序展开

- **它能做什么**：用一个真实的场景或简短示例介绍用途和结果。有实际演示或截图时，挑一个最能说明用法的放在前面。
- **怎么开始**：给出经过核对的最短路径。写清要点哪个入口、选哪个文件夹或运行什么命令，以及成功后会看到什么。
- **怎么用、怎么工作**：按真实用户操作和对应结果来写。状态较多时用小表格，工作流复杂时用步骤图。将少数读者需要的细节放到折叠区。小项目可以合并章节。
- **哪里容易卡住**：只留与仓库实际使用有关的限制和常见问题。隐私、权限、开发和测试有需要再写。
- **关于作者（可选）**：有适用且已确认公开的资料时，放在文末。

## 可选的作者区

1. **先完成正文。** 写出一份可用的 README。保留原有的作者署名、维护团队和许可证要求的归属。新增个人资料由使用者决定，GitHub 仓库所有者和提交记录仅用于核对项目。
2. **优先用已经确认的资料。** 使用者已经明确选择添加并提供公开字段，或在自己的 Skill 里填写了[可选作者档案](references/author-profile.md)，直接使用适用于当前项目的字段。项目的确认资料或当次指示优先。用户明确要求写成无作者区时，省略新增的作者区。
3. **首次缺资料时随稿问一次。** 先给出正文，再在聊天中问：「要在文末加『关于作者』吗？如果要，发我你愿意公开的署名、GitHub、个人网站、公众号或联系方式，选你想写的就行。」用户已回答过或明确要求跳过时，直接继续。可先交付正文并省略整个作者区。
4. **有多少写多少。** 收到资料后，按当次的授权范围更新草稿或 README 文件。只有一个署名时，一句署名就够了。公众号只有名称时，写微信内可搜索的名称。有公开主页、文章或二维码时，可以用使用者给的入口。省略空栏、占位符和空作者区。
5. **按使用者要求保存。** 本次提供的资料用于当前项目。使用者明确要求以后复用时，可把其确认可公开且希望设为默认的字段写进自己安装的作者档案。也可以由使用者直接填写。街道地址、私人邮箱和个人手机号只有在使用者明确选择公开后才使用。「地址」优先理解为个人网站或主页链接。

## 交付前检查

- 核对 Markdown 的标题锚点、相对路径和截图。核实徽章的文字、图片与点击目标，安装步骤能从读者能拿到的文件起步。
- 草稿、写入本地和同步 GitHub 都按当次请求进行。获得推送授权时，沿用目标仓库和可见性，推送后回读远端 README 和提交。作者区以用户同意发布的字段为准。
